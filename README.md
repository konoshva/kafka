# Спринт 1. Базовая эксплуатация Apache Kafka. Практическая работа
## Структура приложения
### Класс TopicChecker
Вспомогательный класс. Проверяет в бесконечном цикле наличие топика my_topic, после появления которого завершает работу. 
Завершение TopicChecker используется в docker-compose.yml как условие запуска сервисов producer и *_consumer. Это позволяет 
создать топик my_topic в интерактивном режиме, а также избежать преждевременного запуска остальных сервисов без определения 
healthcheck для брокеров Kafka.
### Класс ProducerJson
Отправляет в синхронном режиме в топик my_topic 100 сообщений с использованием JSON сериализатора и Schema Registry. Выводит 
на консоль информацию об отправленных в топик сообщениях, так же как и информацию об ошибке, в случае ее возникновения (завершая
при этом работу).
### Класс SingleMessageConsumerJson
Получает сообщения из топика my_topic в режиме автофиксации, используя JSON десериализатор и Schema Registry. Выводит в 
консоль каждое полученное из топика сообщение. В случае ошибки обработки сообщения выводит в консоль информацию об ошибке 
и переходит к обработке следующего сообщения.
### Класс BatchMessageConsumerJson
Получает сообщения из топика my_topic с использованием JSON десериализатора и Schema Registry. Использует управляемый режим
фиксации сообщений с помощью которого обрабатывает сообщения пакетами. При этом информацию об обработке каждого полученного
сообщения выводит в консоль. Кроме того, отдельной строкой сообщает о факте фиксации пакета сообщений (что позволяет проинспектировать
какие именно сообщения были добавлены в пакет). В случае ошибки обработки сообщения выводит в консоль информацию об ошибке 
и переходит к обработке следующего сообщения, не отменяя обработку пакета.
## Инструкция по запуску приложения
Перейдите в корневую папку и запустите команду разворачивания инфраструктуры:

    docker-compose up -d

Система перейдет в режим ожидания при создании контейнера **kafka-topic_checker-1**, что будет отображаться как длящийся процесс 
запуска контейнера. 

С помощью [Kafka UI](http://localhost:8080/) убедитесь, что развернуты 3 брокера Kafka.
Выполните в другой консоли код для создани топика my_topic:
    
    docker exec -it kafka1-1 kafka-topics --create --topic my_topic --bootstrap-server kafka1:9092 --partitions 3 --replication-factor 2

При этом в первом окне завершится работа контейнера **kafka-topic_checker-1**, после чего будут запущены контейнеры:
* **kafka-producer-1** (завершится после отправки ста сообщений в топик my_topic)
* **kafka-batch_consumer-1**, **kafka-batch_consumer-2** (прочитает сообщения топика, но продолжит работать в режиме ожидания новых сообщений)
* **kafka-sm_consumer-1**, **kafka-sm_consumer-2** (прочитает сообщения топика, но продолжит работать в режиме ожидания новых сообщений)

Прочитать отправленные сообщения можно командой:

    docker logs kafka-producer-1

Здесь можно посмотреть, какие именно сообщения отправил producer.
Альтернативно, можно посмотреть лог контейнера в UI DockerDesktop.
Аналогичным образом, подставляя имена контейнеров получателей, можно посмотреть принятые ими сообщения. В kafka-batch_consumer-1
и kafka-batch_consumer-2 можно увидеть сообщения о пакетной фиксации смещений.

Список запущенных контейнеров (и их имена) можно получить командой:

    docker-compose ps

Еще один вариант контроля - проинспектировать Kafka кластер с помощью [Kafka UI](http://localhost:8080/):
* Перейти на вкладку **Topics** и убедиться, что топик my_topic содержит 100 сообщений
* Перейти на вкладку **Consumers** и убелиться, что обе консьюмер группы consumer-group1 (к ней принадлежат kafka-sm_consumer-\*)
  и consumer-group2 (к ней принадлежат kafka-batch_consumer-\*) не содержат не обработанных сообщений (значение в поле **Messages
  Behind** должно быть равно нулю)
* Кроме того здесь же можно увидеть все сообщения топика
